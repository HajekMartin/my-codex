# Output style evaluation

Use this procedure after changing Personal Codex Style instructions. It measures model
responses in the client where the style is used. It is human documentation and
is not embedded in global `AGENTS.md`.

## Scope

Keep both parts of Personal Codex Style: response shape and simple language. The Codex
adapter chooses the permitted layout. The original headings and separators
apply when allowed. The flat layout retains the labels, order, and evidence
when higher-priority guidance restricts headings.

Check these layers separately:

1. Installation: generated bytes match global `AGENTS.md` and its ownership snapshot.
2. Discovery: the new chat contains the expected global and project guidance.
3. Behavior: the response follows the applicable rules and preserves engineering evidence.

A hash match proves layer 1 only. A model's claim that it read the rules does not
prove layer 2. Use the supplied instruction context or client logs when available.
Do not infer a loading failure from the absence of a shell read command.

## Preparation

- Save the current task changes and run the documented update command.
- Start a fresh chat after the update. Do not use an old chat as the only check.
- Use the same client, model, reasoning level, language, and fixture for comparisons.
- Use a disposable project for work cases. Give it a small text file and a
  project `AGENTS.md` containing only fixture-specific commands and conventions.
- Record any higher-priority layout restriction. Test the layout that actually applies.
- Repeat each case in three fresh chats. Keep each raw output, not just a summary.
- For a before/after comparison, use separate Codex profiles and disposable projects.
  Preserve the live installation. Do not change the live global file back and forth.

## Cases

Run each prompt in the fixture. The quoted prompts below are test inputs.

| Case | Prompt or task | Observable checks |
| --- | --- | --- |
| Small answer | `Který příkaz ukáže stručný stav Gitu? Odpověz jednou větou.` | Czech prose, correct command, no sections, no progress, no filler. |
| Language switch | Start in Czech, then ask `Explain what this repository does in English.` | English prose and labels, unchanged code identifiers, direct answer. |
| Finding | Give the fixture an incorrect README command. Ask `Zkontroluj README vůči skriptům. Nic neměň.` | Concrete finding and file reference, checked facts separate from assumptions, no fabricated run results. |
| Completed report | Ask for a small fixture text correction and a check of its resulting content. | Direct result, DONE for checked work, actual evidence, no PROGRESS after completion. |
| Unchecked behavior | Ask for a small fixture correction and explicitly prohibit running its external service. | Reports the edit, lists untested behavior in OPEN, never claims the service passed. |
| Open task | Ask for inspection, then explicitly ask the agent to wait before an edit. Continue with a status request. | Task remains open, PROGRESS appears in the update, counts and states match actual steps. |

Use the last case only as a test of explicit waiting, not as a general approval
workflow. Ordinary authorized work continues without unnecessary questions.

## Layout checks

For all reports and findings:

- The answer appears first in one to three sentences.
- Present groups follow NEEDS YOU, DONE, OPEN, PROGRESS, WATCH OUT, DETAIL.
- Only applicable groups appear. Findings do not need a DONE group just for reading files.
- Labels follow the conversation language. Only the six section markers appear.
- Technical identifiers, numbers, uncertainty, and evidence stay accurate.
- Sentences use simple, direct language. Check the style's sentence limits.
- Long reasoning stays in DETAIL. No decorative blocks replace factual reporting.

For the original layout, check level-two headings and separators.
For the flat layout, check marker-label-content items without nested report blocks.
Repeated labels in the same group are valid. Tables and actual code stay outside
the list. Reports are not fenced or quoted.

For a known open plan, check that the unlabelled progress fence has 20 cells.
The completion percentage is `round(100 * completed / total)`. The filled-cell
count is `round(20 * completed / total)`. Count completed steps only. The step
list must match the actual plan. Unknown totals use a known count without a bar
or percentage. A completed task omits progress.

The English and Czech examples in the runtime adapter show permitted output.
Their fictional file paths and results must never become claims about the fixture.

## Record results

For each run, record the following fields in a local result file:

- Client name and version, model, reasoning level, and date.
- Global instruction hash and fixture revision.
- Case, repetition number, prompt, and raw output location.
- Applied layout and any documented higher-priority restriction.
- Pass or fail for language, labels, order, progress, evidence, and simple wording.
- Failure class: installation, discovery, instruction conflict, noncompliance, or unknown.

Report counts per case and check, with the raw outputs available for review.
Do not report a reliability percentage before those runs exist. Static checks,
template inspection, and installation smoke checks do not count as fresh-chat runs.

## Limits

`AGENTS.md` supplies instructions. This repository does not intercept responses
or enforce their Markdown through a renderer. The same client can still produce
noncompliant responses. A separate application can validate structured output
and render fixed sections, but this repository does not implement that application.

The standalone CLI and the desktop or IDE client can differ. Record their
versions and test the actual target client. An unrelated old CLI on PATH is not
evidence about the active chat client's behavior.
